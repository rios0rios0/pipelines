# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

When a new release is proposed:

1. Create a new branch `bump/x.x.x` (this isn't a long-lived branch!!!);
2. The Unreleased section on `CHANGELOG.md` gets a version number and date;
3. Open a Pull Request with the bump version changes targeting the `main` branch;
4. When the Pull Request is merged, the `release.yaml` workflow automatically creates a Git tag and GitHub Release.

Releases to productive environments should run from a tagged version.
Exceptions are acceptable depending on the circumstances (critical bug fixes that can be cherry-picked, etc.).

## [Unreleased]

### Added

- added `global/scripts/tools/dependency-updates/`, which reports every pinned third-party dependency that has a newer version upstream, and `.github/workflows/dependency-updates.yaml`, which runs it **twice a week** (Monday and Thursday, 06:00 UTC) and **fails the build** when anything is stale. Pinning is only half a policy: it stops a dependency moving without a decision, but a pin never announces that it is three CVEs behind, so the missing half is something that tells a human when to decide. It covers all four pinned surfaces -- GitHub Actions (newer release for the action), container images (the pinned tag now resolves elsewhere), binaries and packages (newer version upstream), and the handful of versions written a second time in a template that has no `SCRIPTS_DIR` to read the manifest from. `make check-dependency-updates` runs the same check by hand; `make test-dependency-updates` validates the checker offline against fixture upstreams
- added a `# upstream: <kind> <coordinate> [track=<major>]` annotation to every pin in `global/scripts/shared/pinned-versions.sh`, naming where that pin's releases come from. A pin with no annotation is reported as untracked and **fails** the check rather than being skipped quietly, because coverage otherwise shrinks one forgotten annotation at a time while the job stays green. `track=` exists for pins deliberately held back -- GoReleaser is on `1.x` because `2.x` is a breaking configuration change, and without it the check would report that migration as an update on every run until somebody muted the job
- added `.dependency-updates.json` support (`{"ignore": ["glob", ...]}`) for genuinely ROLLING references such as `alpine:edge`, which is rebuilt almost daily. It is empty by default: a check that is always red stops being read, but silencing something by default would hide the ordinary stale pins the tool exists to find


### Fixed

- fixed the shared preamble in `global/scripts/shared/cleanup.sh`, which tested whether `~/.local/bin` was on `PATH` at all rather than whether it came FIRST. On a persistent or self-hosted runner that directory is very often already on `PATH` -- from a login profile, a service unit, or a tool that ran earlier -- and when it sits AFTER a directory holding a system-wide copy of the same tool, the membership test passed, the preamble did nothing, and the pinned version installed into `~/.local/bin` was silently shadowed by whatever copy happened to be there first. Every tool script that installs there documents the opposite guarantee ("our copy wins over a system-wide one"), and thirteen of them depend on it, so the pin was decorative on exactly the hosts where a stale system-wide install is most likely. The guard now tests precedence and prepends unless the directory is already leading; a duplicate left further along `PATH` is harmless, since lookup stops at the first match. An ephemeral runner starting from a clean `PATH` is unaffected -- it never had the directory in the first place, so the old guard and the new one both prepend it
- fixed the Semgrep pin check in `global/scripts/tools/semgrep/run.sh`, which verified the pin by parsing `semgrep --version` -- not a reliable report of what is installed. The entry point dispatches either to the OCaml CLI or to the legacy Python one, and on 1.173.0 the two disagree: a clean virtualenv holding `semgrep==1.173.0`, on a machine with no other Semgrep and none on `PATH`, answers **`1.162.0`** to `semgrep --version` while `pip show semgrep`, `importlib.metadata.version("semgrep")`, `semgrep.__VERSION__` and `semgrep-core -version` all answer `1.173.0`. The pin could therefore never be satisfied for that release, and every run failed claiming another Semgrep was shadowing the install -- for a version that was installed correctly and was the only one present. The check now asserts two things that are this script's own to assert and do not route through the CLI: `semgrep` on `PATH` resolves to the launcher this script symlinks, and the distribution installed in this script's virtualenv is the pinned version. A genuinely wrong version still fails, which was verified alongside the fix
- fixed `global/scripts/tools/semgrep/run.sh` reporting a cause it had never checked. Its post-install failure said "Another Semgrep earlier on PATH is shadowing ..." for every reason the check can fail, and shadowing is only one of them -- the version-reporting mismatch above, a virtualenv that could not be created, or a `pip install` that failed all produce exactly the same message, which then sends the reader hunting through `PATH` for something that is not there. The two install steps are now checked (a distribution without the venv module and a failed wheel install each fail with their own message, and pip's output is captured so a failure can say why in its own words), and the failure reports what was OBSERVED -- the path `semgrep` actually resolves to, the path it was expected to resolve to, and the version the virtualenv actually holds

### Security

- **BREAKING CHANGE:** installed JavaScript dependencies with lifecycle scripts DISABLED (`npm ci --ignore-scripts`, `yarn install --mode=skip-build`) in every lint, test, knip and SBOM job on all three platforms. A plain install executes `postinstall` from every package in the transitive tree, as the CI user, before any of the project's own code runs -- the npm supply-chain execution path in its most direct form. **Projects that genuinely need those scripts** -- native module builds, `prisma generate`, Playwright browser downloads, `husky` -- **set `install_run_scripts: true`** (GitHub Actions input, forwarded through the `*-docker`, `*-library` and `*-cloudflare` workflows) or `INSTALL_RUN_SCRIPTS: true` (Azure DevOps parameter), and the scripts then run through `npm rebuild` / `yarn rebuild` after the tree is on disk
- **BREAKING CHANGE:** the Azure DevOps JavaScript code-check job now FAILS when a project has neither `yarn.lock` nor `package-lock.json`, instead of falling back to `npm install`. A resolution performed at CI time is not the resolution anyone reviewed, so the job was testing a dependency set that exists nowhere else. The GitLab SBOM job moves from `npm install` to `npm ci` for the same reason -- an inventory built from an unpinned tree describes nothing
- delegated `sca:govulncheck` on Azure DevOps and GitLab CI to the shared runner, which GitHub Actions already used. Inlining `go install` kept a third copy of the pinned version, and three copies drift one bump at a time; the runner reads it from `pinned-versions.sh`, resolves the install directory from `go env GOBIN` instead of assuming `GOPATH/bin`, and writes the JSON report both platforms now publish
- dropped root from the `mssql-tools18` image, which only invokes `sqlcmd` against a remote server. The `awscli`, `golang-awscli` and `bfg` images deliberately still run as root and say why in a comment: the first two are GitLab CI job containers, where the runner clones into `/builds` and a non-root build container cannot write there without runner-side configuration, and `bfg` rewrites a git repository bind-mounted at `/code`
- removed every script-injection path SonarCloud reports in the Azure DevOps templates -- 78 findings, all of them BLOCKER, and the reason the project was rated **E** on security. Azure substitutes `${{ }}` into the YAML *before* the agent runs it, so a template parameter or predefined variable interpolated into a `script:` / `inlineScript:` body was script rather than data. Every one now reaches the shell through `env:`, which expands it at run time. `$(Build.SourceBranchName)` is what makes this concrete rather than theoretical: it is a branch name, so anyone who can open a pull request chooses it, and it was being expanded inside the steps that hold the container registry, AWS and Azure credentials. The `RUN_BEFORE_*` / `RUN_AFTER_*` / `BUILD_COMMAND` hooks still run consumer-supplied shell -- that is their purpose -- but through `env:` and `eval`, so a value can no longer terminate the step and append steps of its own. Three hook sites SonarCloud had not yet reported were fixed with them
- enforced HTTPS on every download that could follow a redirect into plain HTTP (`--proto '=https' --proto-redir '=https'` for `curl`, `--https-only` for `wget`), across the Dockerfiles, the shared scripts and the Azure and GitLab templates
- pinned `pdm` and refused source distributions in the three PDM container images. An sdist runs its `setup.py` during the image build, and an unversioned install baked whatever PyPI served that day into the image. The Python 3.9 image is held at `2.26.9` rather than the `2.28.1` the other two use, because PDM dropped Python 3.9 in `2.27` and pip would refuse the newer pin outright
- generated the test database password per run instead of hard-coding `pipelines`. It was only ever reachable on loopback, so nothing leaked -- but a well-known password is still well-known, and no scanner can tell one in a template apart from a real credential
- replaced the illustrative secret in `global/scripts/tools/gitleaks/.gitleaks.toml` with a placeholder. It came from the upstream sample config and was never live, which is exactly why it is worth removing: it is indistinguishable from the real thing to every tool that reads the file
- moved `contents: write` in `release.yaml` from workflow level to the two jobs that need it. The effective permission is unchanged today; what changes is that a future job added to that file no longer inherits write access to the repository
- validated the report paths the Dart analyze reporter and the Terraform order-check build before writing to them. Both legitimately accept an absolute output directory, so the directory itself is deliberately not confined -- what is confined is the file name each script appends to it

- **checksum-verified the `yq` download, and closed the assertion that could not see it was missing.** `golangci-lint/run.sh` fetched golangci-lint through `download_verified` and `yq` through a bare `curl` a hundred lines above it, with the version hard-coded rather than declared in `pinned-versions.sh` -- so the one binary that parses every consumer's `.golangci.yml` was the one binary nothing checked. The supply-chain assertion reported the file as compliant throughout, because it was a per-FILE `grep -q download_verified`: one verified download anywhere cleared every other download in the same file. It now checks per URL, and is proven to fire against exactly that shape. `YQ_PINNED_VERSION` and four digests (linux and darwin, amd64 and arm64 -- this is the one tool here also resolved on a developer's Mac) join the manifest, read from the `checksums` file published with the release

### Added

- added `global/scripts/shared/pinned-versions.sh`, the single source of truth for every third-party binary these pipelines download, and `global/scripts/shared/verify-download.sh`, the integrity-checked downloader every installer now routes through. Both are sourced, never executed. Each version stays overridable from the environment so an operator can respond to an upstream CVE without waiting for a release here; `pinned_digest` refuses to reuse a committed digest against an overridden version -- verifying new bytes against an old digest would fail every time and read like an attack -- and names the variable that restores verification instead
- added `global/scripts/languages/terraform/{tflint,terra}/install.sh`, pinned and checksum-verified installers replacing the vendors' `curl | sh` one-liners on all three platforms. TFLint's zip is unpacked with `unzip` or, where that is absent (alpine and the `*-slim` images), Python's stdlib `zipfile`, matching how the Dart SDK archive is already handled
- added `make test-supply-chain` (`.github/tests/test-supply-chain.sh`), 23 assertions holding the whole contract: actions pinned to SHAs and carrying their version comment, images and `FROM` lines digest-pinned, no remote script piped into a shell, every release download routed through `download_verified`, every committed digest well-formed, every package install naming a version, every `scripts-repo` abstract honouring an explicit ref, and no example teaching consumers to track `@main`. Pinning is not a state you reach but one you keep, and every finding here was introduced by someone doing something reasonable -- copying a vendor's documented one-liner, or adding an action the way the marketplace prints it
- added checksum verification to the Dart and Flutter SDK downloads, against the `.sha256sum` and the `releases_linux.json` `sha256` field Google publishes. This is deliberately weaker than the pinned tools and the comments say so: the SDK version is the consumer's to choose, so no digest can be committed here, and a compromised publisher would serve a matching checksum too. It still catches a truncated transfer, a cache serving wrong bytes, and any tamper that cannot also rewrite a second HTTPS request

- added a regression assertion (`test-yaml-merge` Test 9) that fails when any test script invokes a bare `yq` instead of the resolved `$YQ`. A bare invocation is what every yq example on the internet looks like, and the failure it causes appears only on machines nobody runs CI on. Comment lines are stripped before matching, for the same reason the supply-chain suite strips them -- this repository documents the patterns it forbids at length, so the paragraph explaining the rule would otherwise break it. Proven to fire against a deliberate violation

- added `make test-azure-step-names` (`.github/tests/test-azure-step-names.sh`), which EXPANDS every Azure DevOps template -- following `template:` includes and unwrapping the `${{ if }}` / `${{ each }}` blocks a naive walk skips -- and asserts three things at once. First, that every template PARSES and every include RESOLVES: a template that does not parse expands to no jobs, so the other two assertions would find nothing wrong and pass for the worst possible reason, which is the same silent-pass shape this test exists to prevent. Second, that no job declares a step `name:` twice; that defect has now shipped four times and nothing in CI could see it, because the YAML is valid, ShellCheck does not read it, and no pipeline in this repository ever runs, so the first execution is always in a consumer's project. Second, that every job referencing `$(Scripts.Directory)` actually checks the scripts out -- the opposite failure, an empty variable and an exit `127`, whose obvious fix is to add the include that creates the duplicate. Those two have to hold together or fixing one reintroduces the other. Every assertion was proven to fire against a deliberate violation, and none trips on another's
- added the `GO_TEST_INTEGRATION_PARALLEL` variable to the Go test runner (`global/scripts/languages/golang/test/run.sh`): it feeds `go test`'s `-p` flag for the integration phase, so a consumer whose integration fixtures allocate per-instance resources (for example an embedded PostgreSQL on an OS-assigned port) can run integration packages concurrently and cut the phase's wall time. The default stays `1`, keeping the serial behavior byte-identical for every consumer that does not opt in. The runner reads it from the environment of the job that runs it, which on GitLab CI and Azure DevOps a pipeline variable already is; **on GitHub Actions it is not**, because a workflow that `uses:` a reusable workflow can pass only `inputs` and `secrets` across that boundary, so an `env:` at the call site would silently never arrive. GitHub consumers therefore get an `integration_parallel` input, threaded through `go.yaml`, `go-docker.yaml` and `go-render.yaml` into the test action exactly as `coverage_threshold` already is

### Security

- pinned **every third-party GitHub Action to a full commit SHA** (184 references across 46 files), with the human-readable version kept in a trailing `# vX.Y.Z` comment so the pin stays auditable and Dependabot/Renovate can still propose bumps. A tag is a label the publisher can move at any time, so `@v6` was a promise rather than a pin: a compromised maintainer account or a retagged release would have run inside every consumer's pipeline at once, with the job's token in scope. Same-repository `rios0rios0/pipelines/...@main` references are deliberately untouched -- they share the repository's own trust boundary, `test-workflow-composition.sh` Test 7 requires them, and pinning them is a chicken-and-egg because the SHA cannot exist before the commit that needs it
- pinned **every container image to an immutable `@sha256:` digest** (42 references), and normalised the floating tags to a concrete version first, so `alpine:latest`, `alpine/git:latest`, `golang:latest`, `python:3-alpine` and an entirely untagged `bitnami/kubectl` no longer decide the build environment at pull time. A tag can be repointed at new content, which meant a red build could not be reproduced and a green one proved nothing about tomorrow
- **checksum-verified every binary these pipelines download and execute.** Nothing verified anything before: `gitleaks`, `shellcheck`, `hadolint`, the CodeQL bundle, `flyctl`, `osv-scanner`, `golangci-lint`, ProGuard, `tflint`, `terragrunt`, `stoml`, the GoReleaser `.deb` and the terra CLI were all fetched and run unverified, most of them at whatever version `releases/latest` resolved to that morning. Whoever could answer the request -- upstream, their CDN, or a proxy on the runner's egress path -- chose the bytes that then executed with the job's credentials, which on the SAST jobs includes a token that can write to the repository being scanned. Versions and SHA-256 digests now live in `global/scripts/shared/pinned-versions.sh`, and `verify-download.sh` deletes and refuses anything that does not match rather than merely reporting it
- **removed every `curl | sh` install.** A remote script piped into a shell hands the runner to whatever that URL returns at that moment, with no pin, no checksum and no opportunity to review -- the supply-chain shape this repository's own SAST stage exists to flag. Eleven call sites are gone: TFLint (five, fetched from the `master` BRANCH on all three platforms), the terra CLI (four, fetched from `main`), GitLab's secure-files installer inside the job that holds the project's signing material, and `golangci-lint`. `make setup` no longer pipes `clone.sh` either -- it was the first command a new developer ran, and `clone.sh` only ever did `git clone` / `git pull --ff-only`, so it now does exactly that and fetches no remote script at all
- **a consumer's pin now reaches the scripts, not just the templates.** All three `scripts-repo` abstracts cloned the default branch with no ref, so a consumer pinning `uses: rios0rios0/pipelines/...@4.23.0` got the workflow file from the tag and every SCRIPT it executed from `main`. Pinning the entry point while the payload floats is worse than not pinning, because it reads as covered. The GitHub action follows `github.action_ref`; GitLab and Azure DevOps take a `PIPELINES_REF` variable (still defaulting to `main`, so nothing changes for a consumer who has not opted in). All three accept a branch, a tag **or a commit SHA** -- `git init` + `git fetch <ref>` rather than `git clone --branch`, which rejects a raw SHA -- and each prints the commit it resolved, so a job log alone answers "which scripts did this run execute?"
- pinned every `go install ...@latest` (`govulncheck`, `gotestsum`, `gocovmerge`, `gocover-cobertura`, `go-junit-report`, `cyclonedx-gomod`), every unversioned `pip install` (`pdm`, `vulture`, `semgrep`), `gem install` (`bundler-audit`, `debride`) and `npx --yes knip`. For a linter or scanner this is not only a supply-chain question: the tool that decides whether the code is safe to ship was chosen by whoever published most recently, so an unchanged commit could pass on Monday and fail on Tuesday with nothing in the diff to explain it, and the earlier verdict could not be reproduced
- refused source distributions and install-time scripts wherever a package manager runs on a runner: `--only-binary :all:` on every `pip install` (an sdist executes its `setup.py` AS PART OF THE INSTALL, so it is arbitrary code execution before the tool is ever invoked), `npm_config_ignore_scripts=true` in front of every `npx --yes`, and `--ignore-scripts` on the deploy CLI installs. Each pin was checked to resolve binary-only including its full transitive tree, so the flag costs nothing today and a future bump that cannot resolve is a signal worth reading

### Security

- ensured no deployment credential is ever passed on argv. Every CLI in this family accepts its token through an environment variable (`VERCEL_TOKEN`, `NETLIFY_AUTH_TOKEN`, `CLOUDFLARE_API_TOKEN`, `FLY_API_TOKEN`), and Render -- which publishes no CLI -- is driven with `curl --config -` so its bearer token arrives on stdin. Argv is the wrong channel twice over here: it is world-readable through `ps` for the lifetime of the process on a shared or self-hosted runner, AND the resolved command line is recorded into `command.txt`, which every platform publishes as a downloadable artifact, so a token on argv would be exfiltrated into that artifact and retained for its retention period. Render's deploy hook URL embeds its own secret key in the query string, so the whole URL is treated as a credential and only a redacted placeholder is recorded. Each of these is pinned by a test that feeds a sentinel value and greps the entire report directory for it, so the guarantee cannot regress silently. Same reasoning as `-DnvdApiKeyEnvironmentVariable` in the Dependency-Check runner ([GHSA-qqhq-8r2c-c3f5](https://github.com/advisories/GHSA-qqhq-8r2c-c3f5)): pass the NAME, never the VALUE

It writes a sibling file rather than appending to `variables.tf`, so generated content stays exempt from the order-check's `// SET ON .HCL` marker rule (which a generator cannot satisfy) while remaining visible to the dead-input scan (which globs `*.tf`).
